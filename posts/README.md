# posts — посты для канала

Папка содержит готовые посты для канала и утилиту для их переноса в редактор кабинета.

## Файлы

| Файл | Что это |
| --- | --- |
| `2026-08-02-dropweb-proxy-launch.md` | анонс браузерного расширения dropweb proxy. Внутри два варианта разметки: rich и запасной обычный HTML, плюс плейн-превью и заметки. |
| `richcopy.html` | утилита: кладёт HTML в буфер обмена с флейвором `text/html`. Один файл, без зависимостей, работает офлайн. |

## Как публиковать

1. Открыть `richcopy.html` двойным кликом.
2. Нажать «Загрузить пост dropweb proxy» либо вставить свой HTML в поле.
3. Нажать «Скопировать как HTML» или Cmd+Enter.
4. В кабинете `cab.dropweb.org` → админка → посты в канал: включить тумблер «Rich-пост».
5. В поле редактора Cmd+A, Delete, затем Cmd+V.
6. Проверить предпросмотр и отправить.

## Главная ловушка

Редактор кабинета построен на TipTap (WYSIWYG) и парсит исключительно флейвор `text/html` из буфера обмена. Копирование HTML-исходника из markdown-файла или редактора кода помещает в буфер только `text/plain`. Из-за этого TipTap вставляет теги как видимый текст. При отправке Telegram возвращает ошибку неподдерживаемых тегов, которую кабинет отображает как «Ошибка HTML-разметки сообщения» (код `invalid_html`). Правило: копировать нужно отрендеренное, а не исходник, `richcopy.html` именно это и делает. При этом сама ошибка ничего не говорит о наличии реальных ошибок в разметке.

## Что теряется при вставке через редактор

При проведении поста через интерфейс редактора некоторые элементы схемы сбрасываются.

- Схема TipTap в `zencab/src/components/admin/content/telegramRichExtensions.ts` не содержит узла `footer`, поэтому подвал сворачивается в обычный абзац.
- Атрибуты `bordered` и `striped` у тега `<table>` не объявлены в схеме, поэтому они отбрасываются.

Если нужен байт-в-байт точный пост, редактор надо обходить через `POST /cabinet/admin/channel-posts` с `rich: true` или `sendRichMessage` бот-токеном.

## Ограничения формата

- rich: до 32000 отрендеренных символов, до 50 медиа-вложений; отдельное медиа-поле запрещено, картинка идёт тегом `<img>` внутри HTML со ссылкой только по https.
- обычный режим: до 4096 символов, с медиа подпись до 1024; из тегов Telegram понимает только `b`, `i`, `u`, `s`, `a`, `code`, `pre`, `blockquote`, `tg-spoiler`, `tg-emoji`; переносы строк выполняются символом новой строки, а не `<br>`.
- `details` допустим только на верхнем уровне документа, внутрь `blockquote`, `li` и `td` его схема не пустит.
- Кастомные эмодзи берутся из пака **Zenbot Cabinet** — `t.me/addemoji/zenbot_cabinet_by_dropwebpay_bot`, 134 эмодзи. Пак создан самим `@dropwebpay_bot` (суффикс `_by_dropwebpay_bot` в слаге), поэтому бот вправе их использовать. Ground truth пака: `dropweb-ads/data/emoji-pack-zenbot-cabinet.json`; рабочая карта «символ → id» — `PACK` в `dropweb-app/.github/scripts/notify_telegram.py`. Сверять символы со снятым U+FE0F: пак публикует `⚡`, а в тексте может стоять `⚡️`.
- Пака `dropwebpackv1` НЕ СУЩЕСТВУЕТ — имя было выдумано и разошлось по документам. Старые id вида `5265…` (пост от 2026-08-02) принадлежат прежнему паку и устарели; актуальные начинаются с `544…`/`5442…`.
- Проверено отправкой 2026-08-29: `sendRichMessage` вернул 9 сущностей `custom_emoji` из 9 — эмодзи приходят кастомными, а не деградируют.

## Кастомные эмодзи в КАНАЛЕ бот отправить не может (правило Telegram, не наша поломка)

Дословно из `core.telegram.org/bots/api`:

> Custom emoji entities can only be used by bots that purchased additional usernames on Fragment
> **or in the messages directly sent by the bot to private, group and supergroup chats**
> if the owner of the bot has a Telegram Premium subscription.

Каналов в этом списке нет. Premium владельца покрывает только личку, группы и супергруппы.
Замерено 2026-08-29 одним и тем же HTML: личка `@dropwebpay_bot` → 2/2 `custom_emoji`,
супергруппа → 9/9, канал → **0**. У `@dropwebpay_bot` в `getMe` нет `active_usernames`,
то есть купленного на Fragment юзернейма нет.

Отсюда следствия:

- Старые посты канала с кастомными эмодзи публиковал **сам владелец** (человек с Premium), не бот.
  Пересылок среди них нет — форвард-трюком это не объясняется.
- Пока боту не куплен юзернейм на Fragment, в канале эмодзи будут приходить обычным юникодом.
  Пост при этом остаётся корректным: `tg-emoji` деградирует в свой фолбэк-символ.
- Репетиция в супергруппе **не доказывает** поведение в канале — там эмодзи работают всегда.
  Это ровно та ловушка, на которой я и попался.

## Композер кабинета автолинкует текст — вести через него посты с брендом-доменом НЕЛЬЗЯ

Расширение Link в TipTap включено с автолинком и превращает любой текст, похожий на домен,
в ссылку с префиксом `http://`. В посте Flow.Studio это дало:

- `Flow.Studio` ×3 → `<a href="http://Flow.Studio">`. TLD `.studio` существует, домен резолвится
  (308 → `https://Flow.Studio/` → 400), то есть в посте оказались три кликабельные ссылки в никуда.
- `https://flow.dropweb.org` ×3 → понижены до `http://` (работают через 301, но понижены).

Правило: если в посте есть бренд с точкой внутри, отправлять только напрямую через
`sendRichMessage` по API — тогда HTML уходит байт-в-байт, автолинку неоткуда взяться.

## Опубликованный rich-пост отредактировать невозможно

`editMessageRichMessage` и `editRichMessage` → `404 Not Found`; в документации существует только
`sendRichMessage`. Единственный способ исправить вышедший пост — `deleteMessage` и отправить заново.

## Публичное превью канала отстаёт

`t.me/s/<username>` может не показывать свежие посты часами. Судить по превью о том, что реально
в канале, нельзя — смотреть таблицу `channel_posts` в БД бота или открывать пост по прямой ссылке.
